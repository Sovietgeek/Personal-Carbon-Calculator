## Goal
Change normal email/password registration from email-verification-gated to immediately usable, while preserving BCrypt/password validation, rate limiting, lockout, disabled-account protection, secure access/refresh token handling, refresh rotation, logout/revocation, password reset, optional Google OAuth, strict CSP, and the existing Docker/PostgreSQL/Flyway architecture.

## Findings

- `AuthService.register()` currently sets `enabled=false`, creates a 24-hour verification token, sends verification email, and returns no tokens.
- `AuthService.login()`, `CustomUserDetailsService`, `JwtAuthenticationFilter`, and refresh all use `enabled` as an access/account-status gate. `enabled` is also changed by the admin disable/enable flow, so it cannot simply be treated as an email-only flag.
- `accountNonLocked`, `failedLoginAttempts`, and `lockoutUntil` are independent lockout state and must remain unchanged.
- There is no `emailVerified`/`email_verified` field. The existing verification columns are `email_verification_token` and `verification_token_expiry`.
- `RegisterRequest` has no role field and the entity default is `Role.USER`.
- Password reset already clears reset state, resets lockout state, preserves `enabled`, and revokes refresh tokens.
- The current existing-user OAuth path can issue tokens without explicitly checking disabled/locked state.
- Existing tests encode the old mandatory-verification policy and must be updated rather than weakened.
- Existing workspace changes from the prior CSP/API fixes will be preserved and validated; unrelated refactors will not be made.

## Implementation Plan

### 1. Backend registration policy
Update `AuthService.register()` and the registration response contract:

- Keep request sanitization at the correct boundary, duplicate-email detection, password-strength validation, password encoding, default `Role.USER`, account lockout defaults, and the no-token registration response.
- Set `enabled=true` for a newly registered local password account and keep `accountNonLocked=true`, `failedLoginAttempts=0`, and `lockoutUntil=null`.
- Do not generate or persist a mandatory verification token for normal registration.
- Do not call verification-email delivery from normal registration, so a missing/unavailable SMTP service cannot fail valid password registration.
- Update the controller success message to: `Account created successfully. Please sign in with your email and password.`
- Keep registration separate from login; do not auto-login or return access/refresh tokens from registration.

### 2. Preserve account-state security
Redefine the existing state safely without adding an ambiguous migration:

- `enabled=true`: account is active and may authenticate.
- `enabled=false`: account is disabled and must remain blocked from password login, refresh, and JWT-protected APIs.
- `accountNonLocked=false` plus a future `lockoutUntil`: account is locked; preserve the current five-failed-attempt policy and recovery behavior.
- Update stale comments, audit labels, and messages that call every `enabled=false` account “unverified”; use “disabled” for the active account-status meaning.
- Keep all login/refresh/JWT checks. Do not bulk-enable existing rows.
- Existing `enabled=false` rows remain conservatively disabled because the current schema cannot distinguish a legacy unverified account from an explicitly disabled account. They require explicit admin/manual review; this avoids accidentally re-enabling a disabled user.

### 3. Retain verification code as dormant/legacy functionality
Do not edit historical Flyway migrations, delete verification columns, or destroy historical verification data.

- Keep `/api/auth/verify` and resend-verification code only for backward compatibility/future optional verification.
- Remove the mandatory dependency: normal registration no longer creates verification state and login no longer treats email verification as a separate prerequisite.
- Ensure a legacy verification action never overrides an administrative `enabled=false` state. It may clear/record a legacy token, but must not blindly re-enable the account.
- Keep generic anti-enumeration behavior for verification/resend endpoints.
- Keep password-reset and transactional notification code separate and functional.
- No new migration is expected. If implementation proves a schema change is unavoidable, create a new migration only and document it explicitly.

### 4. Login status and error contract
Audit and align expected exception mapping without exposing internals:

- Preserve the same safe generic message for unknown email, wrong password, disabled account, and locked account so account enumeration is not introduced.
- Keep validation failures as 400, duplicate-email behavior consistent with the project convention, unexpected exceptions as 500, and use the existing authentication failure handler/status convention for bad credentials rather than converting every error to 400.
- Update tests and frontend handling to match the final status contract; do not make a failed login look successful.
- Retain server-side structured logging of exception class/request context without passwords, JWTs, refresh tokens, or secrets.

### 5. OAuth account protection
Keep Google OAuth optional and independent of password authentication:

- Preserve enabled=true for newly created Google accounts because the provider has verified the identity.
- Before linking/updating an existing local/Google account or issuing OAuth tokens, explicitly reject `enabled=false` or locked accounts using the same safe account-status policy.
- Keep the existing OAuth status endpoint and frontend behavior that hides social login when dummy/unconfigured credentials are present.
- Do not add real credentials or broaden CSP. Normal email/password registration must work when OAuth is unavailable.

### 6. Password reset and email behavior
Keep password reset as a separate transactional feature:

- Preserve forgot-password token creation, generic response/anti-enumeration, expiry validation, password-strength validation, old-password invalidation, refresh-session revocation, and lockout reset.
- Preserve `enabled` during password reset so an admin-disabled account is not re-enabled by resetting its password.
- Keep SMTP failures non-fatal for normal registration because registration no longer depends on verification email.
- Keep SMTP failure logging for password-reset/optional notifications.
- Wire the current frontend “Forgot Password?” control to the existing safe forgot-password API if needed, without revealing whether an email exists; retain the existing reset-token handling and do not expose reset tokens in the UI/storage.

### 7. Frontend registration/login UX
Update the active modular frontend only:

- Replace the registration success text so it no longer says “Check your email” or asks for activation.
- After HTTP 201, return to the login form, optionally prefill only the registered email, and never persist/prefill the password.
- Keep terms validation and password-strength validation.
- Make login error display use only the backend’s safe message or the existing safe fallback.
- Keep the event-delegation/CSP architecture; do not add inline handlers or `unsafe-inline`.
- Audit active HTML/JS for mandatory-verification wording and remove only the normal-registration dependency; retain explicit optional/reset messages.

### 8. Tests
Update existing tests that assert the old policy and add focused regression coverage:

- Registration creates an enabled active local user with `Role.USER`, no verification token, and no verification-email dependency.
- Registration still hashes the password, rejects invalid/weak/blacklisted input, rejects duplicate email cleanly, and ignores/rejects attempted `ADMIN`/`SELLER` role injection.
- Immediate register-then-login succeeds without a verification step.
- SMTP/email failure does not fail normal registration; password-reset email behavior remains covered separately.
- Disabled users still cannot log in, refresh, or use a valid JWT; locked users still cannot authenticate; lockout and unlock/recovery remain covered.
- Legacy verification processing never re-enables an explicitly disabled account.
- Password reset still clears reset state, preserves the enabled/disabled account state, resets lockout state, and revokes refresh sessions.
- Existing OAuth tests cover new-user success and disabled/locked existing-account rejection.
- Keep refresh rotation, token reuse detection, logout/revocation, cookie-security, CSRF/CORS, authorization, and CSP regression tests intact.
- Update stale test names/comments from “unverified new user” to the final active/disabled policy.

### 9. Verification
After implementation:

1. Run focused auth tests, then `mvn clean test` and `mvn clean package`; record actual totals, failures, errors, and skips.
2. Run `docker compose down`, then `docker compose build --no-cache`, then `docker compose up -d`.
3. Verify PostgreSQL health, Flyway completion, Spring Boot readiness, and the actual served frontend/JS.
4. Against the rebuilt Docker/PostgreSQL stack, perform a fresh browser acceptance flow:
   - Register a new account with email/password → HTTP 201, account row exists, `enabled=true`, `role=USER`, no verification prerequisite.
   - Immediately log in with the same credentials without opening/checking any email → HTTP 2xx and authenticated UI.
   - Confirm response contains intended user/access data only; no password, JWT secret, or refresh token in JSON.
   - Confirm `ecoverse_rt` is an HttpOnly, Secure, SameSite/path-scoped cookie and refresh rotation works.
   - Reload, confirm session restoration through the cookie architecture, open Account and Dashboard, log out, verify refresh fails after logout, then log in again.
5. Run duplicate/invalid/role-escalation/disabled/locked/password-reset checks against Docker PostgreSQL.
6. Confirm the frontend uses `/api/shop/cart` and the corrected feature API prefixes.
7. Confirm unconfigured Google OAuth is hidden/optional and does not affect password auth; geolocation denial remains a handled browser permission state.

## Deliverables

- Backend immediate-activation registration policy with preserved account disablement/lockout/security.
- Dormant/legacy verification code retained without being a login prerequisite or re-enabling disabled accounts.
- Frontend registration success/login UX updated to remove mandatory email-verification messaging.
- Password reset and transactional email behavior preserved.
- OAuth disabled-account protection and optional configuration behavior preserved.
- Updated authentication regression tests and a final report covering architecture, removed/retained verification behavior, account states, password reset, existing users, exact files, tests, Docker, and real browser results.

The implementation will not claim completion until the rebuilt Docker environment passes the real browser sequence: registration → immediate login → Account → refresh/reload → logout → refresh rejection → re-login.
